# Audit de cohérence de l'architecture

Date : 10 octobre 2026. Verdict : **cohérente avec réserves**. Les frontières et le premier sous-ensemble livré correspondent à la cible ; les contrats et parcours étendus, le correcteur et l'isolation n'ont pas encore les preuves nécessaires à une adoption officielle. Cette conclusion ne valide ni un correcteur universel ni une intégration de production.

## Défauts historiques à conserver dans les rapports de migration

Les [huit rapports](compatibility.md#huit-rapports-de-compatibilité) font foi pour les observations du corpus, sans exécution de JS : 36/64 ont des options sans ID ; 78 peut avoir deux distracteurs mathématiquement égaux (u0=1) ; 96 admet une hypothèse de croissance fausse pour k=1,u0=3 ; 103 présente une collision de flags et un graphe non transcrit ; 106 possède deux questions, une exclusion dépendante et computed c négatif malgré bornes positives. Logarithmes/racines/infini/exponentielle ne sont pas couverts par la politique native `rational-value`. Corriger/migrer ces définitions nécessite un choix explicite, pas une « parité » avec leurs bugs.

## Surarchitecture et duplications évitées

Un seul modèle de question par ID ; pas de tables d'attendus concurrentes ni types de sous-exercice à chaque question. Liste/sections suffit aux besoins retenus, sans récursion de parties. Un tuple générique remplace doublet/triplet ; une formule computed construit les recettes sans moteur par famille. Graphes/tableaux/arbre/vecteur/plan complexe demandent des branches de données et quelques calculs communs, pas douze engines autonomes. `instantiateExercise`/`projectPublicInstance` sont les noms concrets, sans aliases generateInstance/prepareDisplay. Admin ne reçoit ni moteur propre ni composant d'édition dans le cœur.

Le package UI peut être un sous-package frère quand les consommateurs le justifient ; aucun monorepo, service réseau ou dépendance ajouté pour cette documentation. L'isolation est une propriété de l'hôte à démontrer, pas un argument suffisant pour imposer un microservice.

## Vérifications et limites du verdict

La matrice rattache chaque capacité à un responsable, un statut et une preuve manquante ; les JSON cibles sont des brouillons refusés par v1. Les textes historiques des lots restent datés pour éviter de les lire comme état actuel. Les commandes de vérification réelles et hashes avant/après figurent dans progress.md. Aucun code métier, contrat/test/fixture, dépendance ou dépôt voisin modifié par cette mission ; aucune migration, DB/production, commit, CI distante ou navigateur exécuté.

Preuves nécessaires avant validation d'adoption : constructeurs/validateurs multiéléments et groupes, méthodes exactes de comparaison et forme, projection exhaustive par branche, gestion serveur des tentatives partielles, processus terminés à échéance et récupérés, tests FastAPI/Colyseus de falsification, rendu réel MathLive, conversion individuelle des exercices utilisés, bundle consommateur et compatibilité d'upgrade. Leur absence impose les réserves ; elle ne demande pas de réécrire les fondations.

Prochaine étape recommandée : **sur instruction distincte**, revoir le contrat de composition/valeurs/groupes puis engager le complément 4 bis ; ensuite 5 étendu, correction et isolation selon dépendances. Le scénario rationnel natif peut servir au premier correcteur sous profil borné sur demande distincte, sans prétendre livrer toute la cible. Aucun lot suivant n'est engagé ici.
